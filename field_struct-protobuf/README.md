# field_struct-protobuf

[Protocol Buffers](https://protobuf.dev) for [field_struct](https://github.com/aemadrid-twx/field_struct) classes, built at runtime with no `protoc` step. You get the `.proto` file to hand to other teams, a message class registered with `google-protobuf`, and instances to and from protobuf binary.

> **Status: 0.1.0, unreleased draft.** Install it from git for now:
>
> ```ruby
> gem 'field_struct-protobuf', git: 'https://github.com/aemadrid-twx/field_struct-adapters', glob: 'field_struct-protobuf/*.gemspec'
> gem 'field_struct', git: 'https://github.com/aemadrid-twx/field_struct', branch: 'develop'
> ```

## Field numbers are yours

Protobuf identifies a field by its number on the wire, not its name. So every field declares one:

```ruby
require 'field_struct/protobuf'

module Billing
  class Invoice < FieldStruct::Base
    required :id,     :uuid,        proto: {number: 1}
    required :total,  :big_decimal, round: 2, proto: {number: 2}
    required :at,     :time,        zone: 'America/Denver', proto: {number: 3}
    required :status, :symbol,      enum: %i[open paid], proto: {number: 4}
    optional :tags,   :array,       of: :string, proto: {number: 5}
  end
end
```

The gem never numbers fields for you. Numbering by declaration order would make reordering two lines a silent wire-format break, because old bytes would decode into the wrong fields. A missing number, a number used twice, or one of protobuf's reserved numbers (19000–19999) raises an error naming the field.

Once a message is in use, treat its numbers like a database column: never reuse a removed field's number.

## The .proto file

```ruby
puts FieldStruct::Protobuf.proto(Billing::Invoice)
```

```proto
// field_struct/billing/invoice.proto: generated by field_struct-protobuf from Billing::Invoice.
// Field numbers come from each field's proto: {number:} option.

syntax = "proto3";

package billing;

import "google/protobuf/timestamp.proto";

message Invoice {
  optional string id = 1;
  optional string total = 2;
  .google.protobuf.Timestamp at = 3;
  optional string status = 4;
  repeated string tags = 5;
}
```

Commit it, or publish it from CI, so a Go or Python service can generate its own code. The package comes from the class's modules (`Billing::Invoice` is `billing.Invoice`), and each class is its own file, importing the files of the structs it refers to. The specs compile this text with `protoc` and check it matches the descriptor the gem registers, field by field.

## Binary

```ruby
bytes = FieldStruct::Protobuf.encode(invoice)
FieldStruct::Protobuf.decode(Billing::Invoice, bytes) == invoice  # => true

message = FieldStruct::Protobuf.to_message(invoice)   # a google-protobuf message
FieldStruct::Protobuf.from_message(Billing::Invoice, message)
FieldStruct::Protobuf.message_class(Billing::Invoice) # its class, for gRPC stubs or Any
```

The message class is built and registered in google-protobuf's generated pool the first time you need it, then reused.

## Mapping

| field_struct | protobuf | Notes |
|---|---|---|
| `:string`, `:uuid`, `:email`, `:url` | `string` | |
| `:symbol` | `string` | `enum:` isn't a protobuf enum (see below) |
| `:integer` | `int64` | |
| `:float` | `double` | |
| `:big_decimal` | `string` | `"19.9"`, exact. Protobuf has no decimal type |
| `:boolean` | `bool` | |
| `:date` | `string` | `"2026-11-01"`. `google.type.Date` isn't in google-protobuf |
| `:time`, `:datetime` | `google.protobuf.Timestamp` | Nanoseconds kept. The field's `zone:` offset is restored on decode |
| `:binary` | `bytes` | |
| `:value` | `google.protobuf.Value` | JSON values only. Numbers come back as floats (`1` reads as `1.0`) |
| a FieldStruct class | its message | |
| `:array` | `repeated` | |

Every singular scalar is proto3 `optional` (explicit presence), so an unset field reads back as `nil`, not as `0`, `false` or `""`. That matches field_struct's "missing". The cost is small: a field set to `0` or `""` takes a couple of bytes, where plain proto3 would leave it out.

`serialize :protobuf, order_id: 'orderId'` renames fields in the message, like any other format.

## Limits

These raise rather than guess:

- **Unions and arrays of unions.** A union would be a `oneof` with a number per member, which needs a way to declare those numbers.
- **Arrays of arrays.** Protobuf has no `repeated repeated`.
- **`nil` inside an array.** Repeated fields can't hold it.
- **Structs that refer to each other** (A has a B, B has an A). Each class is its own file, and protobuf files can't import each other. A struct that refers to itself works.
- **Anonymous classes and custom types.**

And these lose information:

- **An empty array and an unset one are the same on the wire.** Both read back as `[]`.
- **A `:value`'s numbers are doubles**, so integers come back as floats and lose precision past 2^53.
- **A time's zone name isn't kept**, only the field's offset (`-06:00`), the same as field_struct-avro.
- **A message is registered once per process.** Changing a class's fields after its message was built (code reloading in development) needs a restart.
